## 一、定位与原则

- **独立框架**：不复用 `heroship.*` / `br_vanguard` / `br_hero_*`，命名空间 `lev_*`，事件空间 `lev`。
- **数据落国家级变量**：不放在舰船本体，避免阵亡丢成长/能量。
- **文件独立**：所有 `lev_*` 一律新建独立文件，不往 `br_*` 文件里塞。

## 二、恒星光谱等级链

### 2.1 等级表与边界（压缩版）

温度从高到低共 7 级：`sc_b/pc_b_star`（顶）→ `sc_a` → `sc_f` → `sc_g` → `sc_k` → `sc_m` → `sc_m_giant/pc_m_giant_star`（底）。**吸收 = 等级 −1（向红端），重燃 = 等级 +1（向蓝端）**；两者必须成对替换——`solar_system = { set_star_class = sc_X }` 配 `change_pc = pc_X_star`（前者星系作用域，后者直接作用于恒星行星）。逐级对照表见 `lev_stellarite_effects.txt` L7-56，边界排除见 `lev_stellarite_actions.txt` L25-38。

边界规则：目标必须是恒星（`is_star = yes`）；吸收下限 `sc_m_giant`、重燃上限 `sc_b`；排除双星/三合星（`is_binary_star` / `is_trinary_star`）与特殊星体（黑洞/中子星/脉冲星/toxoid 星/rift 星）；吸收自伤保护（D5）：本国星系有殖民地时禁止吸收。

> `is_star_class` 实际等价于 `is_system_class`（原版注释），星系与恒星行星两种作用域都能用。

### 2.2 可选扩展（本期不做，登记备选）

|---|---|
| 链尾补 `sc_t`（褐矮星，`pc_t_star`） | 吸收可再降一级逼近死星 |
| 吸干到底坍缩黑洞 | `sc_m_giant` 再吸收 → `sc_black_hole`，本星系殖民地全灭 + 全球外交惩罚 |

## 三、核心资源（国家级变量）

| 变量 | 含义 | 规则 | 上限 |
|---|---|---|---|
| `lev_stellarite_energy` | 恒星能量 | 吸收 +1；重燃 −1；光束 −1 | 0 ~ 10 |
| `lev_stellarite_unlocked` | 解锁 flag | 发放时置位，用于 `potential_country` | — |

成长值已移出噬星者专属变量（2026-09-12 解耦），改由通用利维坦框架的战斗击杀与营养投入两条途径累积（见 `利维坦系统.md`）；吞噬恒星只 +能量、重燃只 −能量，成长不再被扣回。

**乘数坑**：成长属性乘数必须用 `lev_stellarite_growth_level`，不能用无上限累积值（直接当乘数会算出几十万）；用 level 不用 level − 1 是刻意补偿（利维坦没有普通舰队陪跑，开局白送一级）。

**clamp 坑**：`add_variable` / `change_variable` 无原生 clamp，必须用 `if = { limit = { check_variable = { which = X value < 10 } } ... }` 包裹。

### 4.2 作用域（关键，文档 v2.1 此处有误）

```pdx
user_scope = fleet
scope = planet          # ← 不是 galactic_object
```

**恒星在引擎里是一个行星对象**（`is_star = yes`）。选 `planet` 的理由：

- 右键**恒星** → 走 planet 目标路径 ✓
- 右键**整个星系** → 引擎会向星系内**所有合法行星**排队（README `context_menu_ordering` 说明），用 `possible = { is_star = yes }` 一过滤即只剩恒星 ✓

> **一个动作覆盖两种右键姿势**，无需为每个作用域各写一份。

**作用域语义**（易错）：

| 块 | This | 国家引用 |
|---|---|---|
| `possible` | 目标恒星 | `from.owner`（From = 施放舰队） |
| `button_visible` / `button_clickable` | 舰队 | `owner` |

> **陷阱**：嵌套迭代块（`every_system_planet` / `every_fleet_in_system`）会把 `from` 链挤偏。
> 效果开头先 `from.owner = { save_event_target_as = lev_caster }`，之后统一用 event_target 引用。
> `solar_system = { }` 内取施放国用 `fromfrom.owner`（只多一层），再深一层就要 `fromfromfrom`。

### 4.3 其他可用字段（v2.1 文档漏列）

| 字段 | 用途 |

### 4.5 自动托管

玩家可在舰队自动化菜单里给噬星者勾选托管，手动玩法完全不变（不勾就是纯手动）。

四个技能各自带 `automation` 块进菜单：重燃恒星（priority 3，默认关，只在自家星系作业）、恒星光束（priority 1，默认开，星系内有敌舰才开火）、腹中日轮（priority 2，默认关）、恒星暖流（priority 5，默认关，只支援自家殖民地）。

**判断依据**：`automation` 必须写成嵌套块 `automation = { priority = N default_on = yes }`。扁平旧写法 `automation_priority` / `automation_default_on` 在 4.5.1 已失效，引擎报 Unexpected token（`br_arkship_actions.txt` 现有 10 处此类报错，属遗留问题，已单独记录待修）。不写 `ai_minister` 时默认 none，AI 帝国直接忽略，只有玩家用得上。

**吞噬恒星的接法**：官方自动化菜单只能驱动 `scripted_action`，不能直接下灭星器订单，所以加了一个不出按钮的控制面动作 `lev_stellarite_auto_absorb`（`button_visible = { always = no }` + `hide_from_context_menu`）。自动化选中目标恒星并走完 5 天进度后，回调 lev.109 在同一作用域里用 `queue_actions` 下真正的灭星器订单：

```pdx
queue_actions = {
    destroy_planet = { target = event_target:lev_absorb_target skip_fire_phase = no skip_rules = no skip_windup_phase = no }
}
```

这里**只能放 `destroy_planet` 一项**，不要再垫 `move_to` / `orbit_planet`。灭星器订单自带航行与站位，前面垫移动与环绕反而制造打断：环绕是持久订单，会把船按在轨道上，而开火要求恒星正上方站位，两个位置互斥。开火订单被顶掉 → `_unqueued` → 上浮兼解锁，而队列里那条 `destroy_planet` 尚未执行完，队列从头重跑，飞回轨道再下一单 → `_queued` → 再次潜入。死循环由此成立，跟自动化抢目标无关；玩家手动取消也会被队列拉回去。

2026-10-01 实机日志实证：lev.109 只入队一次，而 `_queued`/lev.107 触发 56 次、`_unqueued`/lev.108 触发 55 次、真正的结算回调 lev.103 零次触发。说明后续 55 次下单全部出自队列重跑。`queue_actions` 的官方动作清单（`events/000_fleet_action_examples.txt`）里根本没有 `destroy_planet`，原版全库也无一处 `destroy_planet =`，这一项属自创用法，无先例可参照。

开火定位、模型正对恒星、潜星高回复窗口仍全部由灭星器链路负责，控制面动作只管选目标与把关。它的 `possible` 与 `can_destroy_planet_with_LEV_STELLARITE_ABSORB_BEAM` 同条件，避免自动化挑到灭星器会拒绝的目标；cooldown 30 天防止反复下单。

**满能量时的提示**：能量满（`lev_stellarite_energy >= 10`）时 `possible` 里的 `能量 < 10` 不成立，每个候选恒星都被否掉，引擎只报「没有可用目标」，玩家看不出缘由。因此把上限直接写进自动化菜单那一行的文案（`lev_auto_tt_absorb`），说明满能量时需先用光束或日轮消耗。

这里试过动态提示但**不成立**：`automation` 块的 `tooltip` 字段不解析本地化命令，即使按标准两层写法（`defined_text` 加分支 + 本地化键用 `[名字]` 包裹引用）包好，游戏里仍直接显示 `defined_text` 的原始名。原版全部 10 处 `automation` tooltip 都是静态文本，无动态先例。同样写法在按钮 tooltip 上有效（如腹中日轮按钮里的 `[lev_sun_damage_display]`），是 `automation` 字段独有的限制。

**六个目标控制选项**（`options` 走 inline_script `lev_stellarite_automation_options`，在 `ai.weight` 里用 `FROM = { has_automation_setting = <标识> }` 读取，过滤逻辑在 `lev_stellarite_ai_filters`）：

| 选项 | 标识 | 默认 | 作用 |
|---|---|---|---|
| 自家星系 | `lev_auto_own_systems` | 关 | 吞星会冻伤星系内行星，默认不在自家下口 |
| 友方星系 | `lev_auto_friendly_systems` | 关 | 非敌对的他国星系，默认不碰，免得平白树敌 |
| 敌方星系 | `lev_auto_hostile_systems` | 开 | 敌国星系是主要猎场 |
| 无人星系 | `lev_auto_unowned_systems` | 开 | 无主星系最安全 |
| 有殖民地的星系 | `lev_auto_colony_systems` | 关 | 星系内有殖民地时不吞，避免连带伤害 |
| 有敌舰的星系 | `lev_auto_hostile_presence` | 开 | 有敌对舰队时仍下口，且权重 ×2 优先选 |

> **作用域坑**：`has_automation_setting` 只在自动化选目标期间（动作的 `ai.weight` 或 `possible`）有意义，事件里一律返回 false，也不能用来查询舰队是否处于托管。`scope = self` 的动作（如腹中日轮）候选是舰队自身，权重里要显式写 `FROM = { solar_system = { ... } }` 才能查到所在星系，直接写 `solar_system` 插件会报作用域切换错误。反之 `scope = galactic_object` 的动作（如恒星光束选择器）候选就是目标星系本身，权重里直接写 `any_fleet_in_system` 即可，再套一层 `FROM = { solar_system = ... }` 反而错。

> **待实机验收**：控制面动作能否被自动化正确选中并下单、灭星器订单接上后的实际观感、六个选项在游戏内的显示与生效。

**订单在飞期间封掉自动化**：自动化只认 `ai.weight`，选到新目标就会抢走当前订单，而灭星器从下达指令到结算共 11+169=180 天，中间裸露窗口极大。引擎没有关停托管的脚本接口（`trigger_docs.log` 里 automation 只有 `has_automation_setting`，全库无 set/clear/toggle automation 效果），所以走权重封权：`lev_stellarite_absorb_guard` 作为 `modifier` 被打到 `factor = 0`，五个自动化动作（重燃、光束、日轮、暖流、自动吞噬）全部在 `ai.weight` 里引入它。权重归零后自动化选不到任何目标，等价于托管停摆，订单结束后自动恢复。

判定用双保险：`has_fleet_flag = lev_stellarite_absorbing` 管我方自开的窗口，`has_fleet_order` 直接问引擎当前订单（`destroy_planet_order` / `planet_killer_weapon_windup_order` / `planet_killer_weapon_fire_order`，合法取值出自 `trigger_docs.log`）。窗口由 lev.107 开、lev.108 收，190 天定时兜底防异常中断。只用 `set_timed_fleet_flag` 不用永久 flag，否则链路中途断掉会永久封权。

两个易错点：封权必须排在 `weight = N` 这类加法之后，乘法归零才不会被加回来（光束那条 `weight = 20` 就要求守卫放最后）；`scope = self` 的动作原先没有 `ai` 块，而原版所有带 `automation{}` 的动作都有 `ai{}`，日轮因此补了 `ai` 块才真正能进自动化。

> **待实机验收（关键）**：砍掉队列里的移动与环绕后，`queued`/`unqueued` 是否停止成对刷、订单能否真正跑完 180 天并触发 lev.103。

封权与队列重跑是两回事：封权管自动化选目标，队列重跑则是引擎直接执行队列里残留的 `destroy_planet`，绕过整个 `scripted_action` 体系，因此封权对后者无效。打断源已查明是队列里垫的 `orbit_planet`，见上节。

### 4.6 恒星光束：远程星系选择器（2026-10-02）

**需求**：原版戴森炮那种远程打击，但作用于英雄舰。旧实现是 `scope = self`，只能打舰队**当前所在**星系——要打谁就得先飞到谁那儿，与"恒星炮"的定位不符。

**结论：可以做，且不需要引擎新接口。** 支点在 README 第 37 行：`on_started` 的触发**不要求舰队已抵达目标**（"this action will take place even if the user still needs to travel to the target"）。

**链路**：

```pdx
# 动作：退化成纯粹的星系选择器，自己不推进进度
lev_stellarite_beam = {
    user_scope = fleet
    scope = galactic_object          # 星系图点选目标
    possible = { ... is_in_sensor_range_of_country = from.owner }   # 射程 = 传感器范围
    on_started = on_lev_beam_targeted
    click_to_act_key = lev_beam_click_to_act
    wait = no
    cooldown = 90
    slot = 2
    # 注意：没有 required_progress / progress_activity_key / finish_anim_state
}
```

点选瞬间 → `on_started` → `lev.102`（**system_event**，This = 目标星系、From = 舰队）：

1. `save_global_event_target_as = lev_beam_target@root` —— **必须用 global**：`save_event_target_as` 随事件结束注销，而结算要等 20 天，目标会丢。`@root` 按国家隔离，防多玩家串目标。
2. `after` 块里 `clear_fleet_actions = this` + `clear_orders = yes` + `queue_actions = { wait = { duration = 20 } }` —— 打断选择器排下的行军令，让舰队留在原地（已实机确认瞬间清掉，舰船不动）。写法参照原版 `02_contracts.txt:2434-2443` 对太空生物舰队的"keep them in place"。
3. 锁位：`lev_stellarite_beam_charging`（`ship_speed_mult = -3`，照原版眩晕惯例 `lf_weapon_stun_effect`）+ 锁 `breath_loop` 动画。
4. `fleet_event = { id = lev.106 days = 20 }` 延迟投递开火。

`lev.106`（fleet_event，This = 舰队）结算：主体直接写在事件里（存 `lev_caster` → `lev_stellarite_shot_prepare` 取值 → 打 `event_target:lev_beam_target@root` 内敌舰与爆星特效 → 扣 1 能量）→ 解锁动画 → 播 `beam_fire` → `clear_global_event_target = lev_beam_target@root`。冷却由 action 的 `cooldown = 110` 自点击起算，不再另记舰队 flag。

**为什么进度必须挂事件**：动作在点击瞬间就被自己打断（这是设计的一部分——不打断就会开始赶路），引擎的进度条随订单一起消失，所以 `required_progress` 和原生进度 UI 全部让给事件计时。

**为什么不用 `set_event_locked` 锁位**：它会让舰队变成**不可攻击**（`EVENT_LOCKED_FLEET`），违背"蓄能期可打断/可挨打"，而且它会连舰队自己的订单一起封掉（2026-10-01 在 lev.109 上实测踩过）。改用减速 modifier，动不了但照常挨打。

**两个 ID 冲突别踩**：`lev.110` 已被 `lev_drake_events.txt` 占用，开火事件用 `lev.106`。

**作用域翻转带来的契约变化**：`lev.102` 从 fleet_event 变 system_event 后，`lev.106` 里取施放国的写法从 `from.owner` 改成 `owner`（此时 This 就是舰队），目标也从 `solar_system`（舰队所在地）改成 `event_target:lev_beam_target@root`（选定星系）。改错会**静默打空**，不报错。

## 五、技能效果要点

实现见 `common/scripted_effects/lev_stellarite_effects.txt`。以下是**设计与踩坑要点**：

- **光谱改写**：见 §2.1，成对替换。
- **温度**：`spawn_planet_temperature_effect` + `decrease_/increase_planet_temperature`。每步自带 `reroll_planet` + `clear_blockers`，**副作用见附录 A.3**。
- **`stellarite_low_temp`** 复用原版静态修饰符：吸收时 `add_modifier`（`days = -1` 永久），重燃时 `remove_modifier`。
- **冰封救赎**：`pc_frozen` 且有殖民地 → `change_pc = pc_gaia`，**须在升温前执行**（否则 `pc_frozen` 先被升温链改掉）。
- **外交方向**（v2.1 文档写反）：
  `X = { add_opinion_modifier = { who = Y  modifier = Z } }` 改的是 **X 对 Y 的观感**。
  要让对方讨厌我们，必须在**对方 scope** 下执行、`who` 填**我们**。
- **光束伤害**（v2.1 公式有误）：
  `mult` 是**对累计值相乘**，`base=500 / add=成长 / mult=100` 算出来是 ≈5 万。
  正确写法是两层 script_value：`500 + 成长 × 100`（见 §10.1）。
- **光束敌我筛选**：`event_target:lev_beam_target@root = { every_fleet_in_system = { limit = { controller = { is_hostile = lev_caster } } ... } }`。目标星系是点选时存下的全局事件目标，与舰队开火时的所在地无关（远程打击）。
  `damage_ship` 传入 `attacker` 不会断事件（已确认）。

### 潜星与三态：全部走声明式，不设巡检

潜星不设无敌窗口。`set_event_locked` 经实测会挡住舰队自身订单的推进（lev.109 里加锁后 `destroy_planet` 无法开火），因此弃用；改由 `lev_stellarite_submerged_regen` 提供三防每日 +10% 的高回复硬顶，约 10 天回满。buff 由 lev.107（`_queued`）挂、`days = 190` 与灭星器窗口等长，正常跑完时自然到期，无需回收；订单被取消时走 lev.108（`_unqueued`）摘除。

能量三态（饱食 ≥6 / 饥饿 ≤2）不再由巡检切换 timed modifier，改在 `LEV_STELLARITE_CORE` 里用两个 `triggered_ship_modifier` 的 `potential` 直接判定 `owner.lev_stellarite_energy`。原版先例：`common/inline_scripts/ship_components/behemoth_stage_3_mutations.txt`，同一组件内多块并列亦有先例（`SHIP_BEHEMOTH_GROWTH` 挂了 8 个 inline_script）。

## 六、舰船架构

### 6.1 舰种要点

- `entity = "stellarite_entity"` —— 原版已有。它是**空 locator 网格**，只提供定位器；**可见模型完全来自区段实体**。（这是正常的两段式结构，不是缺陷。）
- 与原版守卫者 `stellarite` 的差异：

| 项 | 原版 | 本舰 |
|---|---|---|
| `is_space_object` | `yes` | **去掉** |
| `num_target_locators` | `0` | `4` |
| `is_designable` | `no` | `yes` |
| `max_hitpoints` | `200000` | `5000` |

- **[已实现] 不要设 `graphical_culture`**：设成 `{ "guardian_01" }` 会导致**舰船设计器里模型完全不渲染**（游戏内正常）。原版 stellarite 用 `no`，而它上一行 `#graphical_culture = { "guardian_01" }` 是**被注释掉的**（官方试过又放弃）。
  但 **`create_ship` 里要写** `graphical_culture = "guardian_01"`——不写会把玩家国家文化套到守卫者模型上，导致染色/光照错误。两者是两回事。
- `enable_default_design = yes` 必须开：`create_ship` / `random_existing_design` 依赖**已存在的设计**。
- **获取顺序不能颠倒**：先 `set_country_flag lev_stellarite_unlocked` → 再 `refresh_auto_generated_ship_designs` → 最后 `create_ship`。因为 `potential_country` 由该 flag 门控，标志未置位时自动设计里根本不会有噬星者。
- **必须自带反应堆与推进器**：原版同套组件靠 `potential`（如 `ship_uses_corvette_reactors`）限定舰种，自定义舰种装不上，会导致 `cannot build any component in the component set power_core` → 设计非法 → **刷船失败**。用 `size_restriction = { lev_stellarite }` 显式放开。
  （`combat_computers` / `sensor_components` / `ftl_components` 无此限制，可沿用原版。）
- **不挂人类科技前置，单档不升级**：噬星者是从恒星里长出来的生物，不会去"研发"裂变能 / 聚变能 / 零点能，也不会因为玩家点了 `tech_thrusters_2` 就换一具新引擎。因此：
  - 星核与能量喷射**均只保留 1 个组件**，无 `prerequisites`（不设 `potential = { have_technology }`）、无 `upgrades_to` 链；
  - 数值取原档位中段（星核 11000 出力 / 1600 合金；能量喷射 −200 出力 / 60 合金），保证设计与刷船不受玩家科技进度影响；
  - 拿到噬星者的瞬间即可用，强度稳定，也免去"开局刷船时玩家还没点出前置科技导致设计非法"的隐患。
  > 对照：先锋级（人类泰坦）走 6 档反应堆 + 5 档推进器并挂 `tech_*` 前置，那是**人类舰船**的做法，噬星者不沿用。
- **命名一律生物化**：这些组件的内核是普通舰船集（`power_core` / `thruster_components`），但噬星者是**生物巨兽**，中文名不能用人造舰的措辞。星核称**噬星者星核**（它吞食恒星物质后在体内炼成的能量器官），推进器称**噬星者能量喷射**（从星核抽取能量向身后喷出），作战电脑称**噬星者神经接口**（把巨兽的感知与意志接驳到指挥链上）。
  参照原版生物舰的命名法：`BIO_PROPULSION` = 生物推进器 / 离子基生物推进器、`BIO_SENSORS` = 重力调制感知器官、`BIO_ARMOR` = 纳米复合甲壳。
  > 原版生物舰（`07_space_monsters.txt`）其实走的是另一套组件集：`thruster_components_bio` / `sensor_components_bio` / `ftl_components_bio` / `neurochips`（**神经芯片**），且**没有反应堆这一项**。本舰沿用普通集是为了复用原版武器与供电体系，仅命名对齐生物风格。
  > 顺带：原版给它自己的生物舰反应堆取名 `BIO_FISSION_REACTOR` = **"裂变代谢"**、`BIO_FUSION_REACTOR` = "聚变代谢" —— 科技词 + 生物词，可作后续命名的参照。

### 6.2 区段槽位（17 槽，压缩版）

布局照抄原版 `stellarite_key`：1 XL + 8 L + 8 PD + `aux_utility_slots = 2`，但**槽位模板必须换成 `invisible_*`**——原版 `large_turret` / `point_defence_turret` 带 `entities` 块会渲染旋转炮塔 mesh，长在生物模型上很违和（完整对照表见 `lev_stellarite_sections.txt`）。PD 槽定位器 `PD_06/PD_07` 都指向 `large_gun_06`，是**原版笔误，照抄不修**。

### 6.3 舰船行为与作战电脑（压缩版）

- `lev_ship_behaviors.txt`：**`combat_movement = player_override` 是战斗中能手动放技能的关键**，缺了就无法手动释放。
- `lev_computers.txt`：11 只利维坦各一台作战电脑（各自 `potential` 限定舰种，`ai_weight = 999` 压过原版电脑），噬星者挂专用 `lev_stellarite` 行为，其余 10 只共用 `lev_leviathan`；中文名按各利维坦生物化命名（噬星者作**噬星者神经接口**）。
- 参考：原版战列舰等作战电脑无法在战斗中接受指令，必须自带。

### 6.4 获取方式：国民理念门控（压缩版）

获取方式已由"收复线"改为**国民理念门控**（2026-09-12 拍板并实施）。

**理念**：`lev_star_overlords`，中文名随政体变化——星海之国（默认）/ 星海企业 / 星海蜂巢 / 星海机械（`swap_type` 按 `has_authority` 切换）。实现要点：

- 图标：`lev_star_overlords.dds`（29x29 未压缩 32bpp，八边形，主色 `#00B38A`，符号色 `#162922`）。

### 8.1 光束伤害数值

**单次伤害 = 500 + 成长等级 × 100**（两层 script_value：外层 `base = 500` + `add = value:<每级小计>`；内层 `base = 0` + `add = owner.lev_stellarite_growth_level` + `mult = 100`，见 `lev_stellarite_values.txt` L3-14）。

## 附录 A、原版温度阶梯映射（含副作用）

> 出处：`common/scripted_effects/00_scripted_effects.txt`（`increase_planet_temperature` 第 179 行 / `decrease_planet_temperature` 第 255 行）

### A.1 升温链（由冷到热）

| 链 | 阶梯 |
|---|---|
| 湿链 | `pc_frozen → pc_arctic → pc_ocean → pc_desert → pc_molten` |
| 干链 | `pc_barren_cold → pc_tundra → pc_tropical → pc_savannah → pc_barren → pc_molten` |
| 高地链 | `pc_alpine → pc_continental → pc_arid → pc_barren → pc_molten` |

### A.2 降温链（由热到冷）

| 链 | 阶梯 |
|---|---|
| 主流 | `pc_molten → pc_desert → pc_ocean → pc_arctic → pc_frozen` |
| 支流 | `pc_barren → pc_arid → pc_continental → pc_alpine → pc_frozen` |
| 旁支 | `pc_savannah → pc_tropical → pc_tundra →` **随机** `pc_frozen` / `pc_barren_cold` |

### A.3 [注意] 副作用（直接影响 D5）

每一步都执行 **`reroll_planet = yes` + `clear_blockers = yes`**：

- 会**重随机数星球 modifier 与地块障碍** → 玩家自家已开发的殖民地被「重燃」洗一遍，deposits / 地形很可能变样；
- **`pc_gaia` 不在任何一条链里** → 盖亚星不参与温度改写，是天然的「安全终点」（正好呼应 §五的 `pc_frozen → pc_gaia`）；
- 到 `pc_frozen` / `pc_barren_cold` / `pc_molten` 后再调用不再变（没有匹配的 `else_if`，静默无效）——**星球温度边界由原版自带，我们不需要自己写 climate 边界**，只需在 UI 上提示。

> 因此 D5 附带一条提醒：重燃虽然不加限制，但**作用于本国已有殖民地时，UI 应提示「此操作会重塑地表（清空地块障碍并重新随机地貌）」**，否则会出现"我只是想救冰封星球，结果把首都洗了"的负反馈。

### A.4 改星的两种原版写法

```pdx
# 写法一：anomaly_events_4.txt:4985-4993 —— 先改星系，再筛 is_star 的主星改 pc
solar_system = {
  set_star_class = sc_m
  every_system_planet = { limit = { is_star = yes } change_pc = pc_m_star }
}

# 写法二：cosmic_storms_events_1.txt:4530-4595 —— 主星 pc 先改，再跳到星系改光谱
random_list = {
  20 = { change_pc = pc_a_star  solar_system = { set_star_class = sc_a } }
}
```

**本方案采用写法一的思路**（`set_star_class` 在星系作用域执行，`change_pc` 直接作用于恒星行星）。

三点已核实结论：

1. `is_binary_star` / `is_trinary_star` 是脚本触发器，可直接写在效果/触发器作用域里。
2. 原版**没有**排除 `sc_neutron_star` 与 `sc_pulsar`（其中 neutron 被当作合法目标）。**我们的方案比原版更保守**（把 neutron / pulsar 也排除）——有意的：玩家技能不该制造脉冲星。
3. `random_list` 的键是**权重值**（`20 = {...}`），不是 `base` / `factor`。

|:--:|---|---|
| 1 | `graphical_culture` | **ship_size 上不要设**（`guardian_01` 会让设计器不渲染模型）；但 **`create_ship` 里要写** `guardian_01` |
| 2 | 槽位模板 | 用不带 `entities` 的 `invisible_*`，否则会渲染旋转炮塔 mesh |
| 3 | 模型结构 | 两段式：ship_size 挂空 locator 网格，**可见模型完全由区段实体提供** |

### B.2 自定义舰种的组件限制

- **必须自带** `power_core` / `thruster_components` 组件（原版靠 `potential` 限定舰种，自定义舰种装不上）。
- `combat_computers` / `sensor_components` / `ftl_components` 无此限制，可沿用原版。
- **作战电脑必须自带**：`combat_movement = player_override` 是战斗中手动放技能的前提。
- 星核 / 能量喷射**不设科技前置、不做档位**：生物不沿人类科技树成长，只保留 1 个组件，拿到即用。

### B.3 其他核实项

| 项 | 结论 |
|---|---|
| `stellarite_entity` / `stellarite_ship_section_entity` | 均存在于 `gfx/models/ships/guardians/stellarite/stellarite.asset` |
| `scripted_action` 的 `scope = planet` | 回调事件类型为 `planet_event`（carrier_event 见 §4.1 行星杀手链路） |
| `required_progress` 单位 | tick 数，最小 2.0 才非瞬时 |
| `cooldown` 单位 | 天 |
| `is_star_class` | 实际等价于 `is_system_class`，星系与恒星行星作用域都可用 |
| `add_opinion_modifier` | `X = { add_opinion_modifier = { who = Y } }` 改的是 **X 对 Y** 的观感 |
| `script_value` 的 `mult` | 对**累计值**相乘（在 `add` 之后） |
| `lev` 命名空间 | 原版仅占用 `leviathans`，`lev` 空置 |
| `stellarite_low_temp` | 原版静态修饰符，可复用 |
| 噬星者模型动画 | `stellarite_ship_section_entity` 有 5 个状态 / 3 个动画（`idle` / `death` / **`attack`**），`attack` 非循环、混合 0.45 |
| 舰船模型两段式 | ship_size 实体是空 locator 网格，可见模型来自区段实体 |

### B.4 守卫者排除清单

原版 `common/scripted_triggers/02_scripted_triggers_enclaves.txt:22` 已列全守卫者/利维坦 ship_size。凡是要筛"玩家舰/守卫者舰"的地方**照抄这份清单**，别自己猜。`lev_*` 新舰种**不在**这份清单里——若要写"是否守卫者"判定，**必须显式排除自己**。
