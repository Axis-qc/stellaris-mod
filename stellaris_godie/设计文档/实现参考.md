# 十七、可行性验证

> 所有 modifier 和命令均已在原版 `G:\SteamLibrary\steamapps\common\Stellaris` 中搜索确认。
> 标注格式：`modifier 名`（原版文件路径:行号）或 `命令名`（原版文件路径:行号）。

## 17.1 全局结论

**整体评估：技能设计中 90%+ 的机制在 Stellaris modding 框架下是可行的。**

少数技能需要调整实现方式（见 17.5），极少数技能不可行（见 17.6）。

## 17.5 需要特殊处理的关键机制

### 17.5.1 永久 modifier 与 `mult` 变量的搭配

`ship_hull_add = X + mult = variable` 的做法在 Stellaris 中**不兼容永久 modifier**（`days = -1`）。永久 modifier 的 `mult` 值在施加时刻固化，无法跟随变量动态更新。

**解决方案**：
- 如果用 `days = -1`：固定修改 modifier 定义中的基础值，不允许 variable
- 如果需要 variable：使用**阶梯式**——每 N 层一个独立的 modifier，达到条件时移除旧 modifier、施加新 modifier

### 17.5.2 循环事件与性能

大量使用循环延迟事件会累加性能开销。建议：

- 能用 modifier 解决的就用 modifier（性能远超事件循环）
- 循环事件内尽量少做重型操作（避免 `every_*` 大范围循环）
- 缩圈/月脉冲等已有全局钩子优先复用

## 17.6 推荐实现次序（基于可行性）

**第一批**（机制最简单、依赖最少）：
- 火力核心：仅需基础战斗 modifier + damage 事件
- 防御核心：防御 modifier + repair 命令 + 维修光环
- 支援核心：命中/追踪/闪避 modifier + repair_percentage + regen modifier（纯 buff 向）
- 命运核心：延迟事件 + modifier 切换

**第二批**（需要多层计数或特殊逻辑）：
- 献祭核心：需要 destroy_ship 循环（注意性能）
- 机动核心：需要星系进入钩子检测
- 控制核心：需要光环组件支持
- 掠夺核心：需要与经济系统整合

**第三批**（依赖武器类型 modifier + 生成管理）：
- 航母核心：create_fleet 批量管理 + weapon_type modifier
- 指挥核心：需要奖励系统 API 支持（如重抽、额外选项）
